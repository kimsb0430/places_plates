사진은 빠르게 담고,
기억은 선명하게 읽는다.

여행지와 식당 사진을 부담 없이 기록하고, 서버에는 업로드 원본을 남기지 않으면서 지도 정보와 개인의 기억을 편안하게 읽는 여행 아카이브 설계안입니다. 첫 버전은 개인 페이지로 시작하고 향후 사용자별 페이지가 있는 커뮤니티로 확장합니다.

3분 사진 10장을 올려 초안 기록을 만드는 목표 시간
01 / PRODUCT

제품 정의

Places & Plates는 사진 갤러리와 여행 블로그의 중간이 아니라, 장소·방문·사진을 연결한 개인 기록 시스템이다. v1은 소유자 한 명의 페이지로 시작하되 모든 기록에 소유자를 명시해 향후 회원마다 독립된 페이지를 가질 수 있게 한다.

📥

빠른 수집

사진을 먼저 올리면 촬영일과 위치를 바탕으로 방문 초안을 자동으로 묶는다.

✍️

가벼운 보완

필수 입력은 최소화하고, 평점·메뉴·비용 같은 정보는 필요할 때 단계적으로 연다.

📖

편안한 열람

사진과 개인 기록을 먼저 보여주고 주소·지도·영업 정보는 보조 계층에 배치한다.

핵심 제품 결정: “완벽하게 작성해야 저장할 수 있는 폼”을 만들지 않는다. 업로드 즉시 비공개 초안으로 저장하고, 나중에 30초 단위로 기록을 보완할 수 있게 한다.
02 / OUTCOMES

목표, 비목표, 사용자 이야기

첫 버전의 성공은 기능 개수가 아니라 “미뤄 두지 않고 기록할 수 있는가”와 “몇 달 뒤 다시 읽고 싶은가”로 판단한다.

목표

  • 사진 10장의 초안을 3분 안에 만든다.
  • 모바일에서 시작한 기록을 PC에서 그대로 이어 쓴다.
  • 공개 이미지의 메타데이터 검출과 처리 완료 후 임시 원본 잔존을 0건으로 유지한다.
  • 여행·장소·방문을 분리해 재방문 기록이 자연스럽게 쌓인다.
  • 사진과 개인 기록을 지도 정보보다 먼저 읽게 한다.

v1 비목표

  • 복사·화면 캡처의 완전 차단 — 웹 기술상 보장할 수 없다.
  • 다른 사람 페이지의 공동 편집 — 향후에도 각 계정은 자신의 기록만 편집한다.
  • 여행 일정 예약·결제 — 기록 경험과 별도 제품 영역이다.
  • 소셜 피드·팔로우 — v1에서는 개인 아카이브 완성도를 먼저 검증한다.
  • 외부 장소 정보의 실시간 동기화 — 비용과 변경 위험을 줄인다.
Story 1

빠른 시작

기록자인 나는 사진부터 올리고 싶다. 그래야 제목과 세부 정보를 정하지 못했어도 기억을 잃기 전에 보관할 수 있다.

Story 2

쉬운 보완

기록자인 나는 자동 제안된 날짜와 장소를 확인하고 일부만 고치고 싶다. 그래야 반복 입력 없이 정확도를 높일 수 있다.

Story 3

편안한 회상

나와 초대받은 방문자는 여행 흐름 안에서 사진과 감상을 읽고 싶다. 그래야 정보 목록이 아니라 실제 경험처럼 기억할 수 있다.

Story 4

안전한 공개

기록자인 나는 원본과 촬영정보를 노출하지 않고 사진을 공개하고 싶다. 그래야 개인정보 유출과 무단 활용 위험을 낮출 수 있다.

Story 5

분류와 분포

방문자인 나는 맛집과 여행지를 나눠 보고 지도에서 기록 수를 확인하고 싶다. 그래야 관심 있는 기록과 지역을 빠르게 탐색할 수 있다.

Story 6

나만의 페이지

향후 가입한 회원인 나는 다른 사람의 기록을 편집하지 않고 내 사진과 장소만 관리하고 싶다. 그래야 독립적인 여행 페이지를 만들고 서로 구경하거나 공유할 수 있다.

03 / PRINCIPLES

설계 원칙

입력 편의와 결과물 가독성이 서로 충돌하지 않도록, 원본 데이터는 구조화하되 작성 화면에서는 필요한 순간에만 항목을 드러낸다.

① Upload first

제목을 정하기 전에 사진부터 올릴 수 있다.

② Smart defaults

날짜·위치·사진 순서는 자동 추정하고 사용자가 확인한다.

③ Progressive fields

제목, 장소, 한줄평 외 항목은 접어 둔다.

④ Story first

결과 화면은 지도 데이터보다 사진과 개인 경험을 먼저 읽게 한다.

C18 구현 기준: 비공개 초안 편집 화면은 제목·방문 월·한줄평을 작성 완료 기준 3개로 안내하고 본문은 선택 항목으로 둔다. 모든 항목은 기존 posts 행에 저장하며, 공개 방문 시점은 사용자가 정한 정책에 따라 일자를 받지 않고 public_visit_year·public_visit_month 쌍으로만 기록한다. 입력이 700ms 멈추면 CSRF 보호 PATCH /api/v1/manage/drafts/{draftId}로 부분 초안을 자동 저장하고, 소유자와 DRAFT 상태가 모두 일치하는 행만 수정한다. 제목을 비운 동안은 저장하지 않으며 실패한 입력은 화면에 유지하고 재시도할 수 있다. 장소 연결은 Google Places를 도입하는 C21 범위로 분리한다.
C21 구현 기준: 장소 검색은 로그인한 소유자가 버튼을 누를 때 Spring Boot의 GET /api/v1/manage/places/search를 통해 Places API (New)에 최대 5건만 요청한다. 결과와 연결된 Google 장소 정보에는 같은 컨테이너의 Google Maps 출처를 유지한다. 선택한 장소는 CSRF 보호 PUT /api/v1/manage/drafts/{draftId}/place로 연결하고 DELETE로 해제한다. Google 검색이 실패하거나 키가 없을 때는 장소명과 선택적인 주소·위도·경도 쌍을 직접 저장한다. Place ID는 장기 보관하고 Google 좌표 스냅샷은 refreshed_at을 기준으로 30일 안에 갱신한다.
C22 구현 기준: 사진 구성은 처리된 썸네일을 인증된 소유자에게만 GET /api/v1/manage/drafts/{draftId}/photos/{photoId}/thumbnail로 제공한다. 각 사진에는 키보드로 접근 가능한 “앞으로”, “뒤로”, “대표로 설정” 버튼과 최대 500자의 대체 텍스트 입력을 제공한다. 배열 순서·대표 여부·대체 텍스트는 600ms 동안 변경이 멈추면 CSRF 보호 PUT /api/v1/manage/drafts/{draftId}/photos로 한 트랜잭션에 저장한다. 서버는 요청 사진 집합이 소유자 초안의 전체 사진 집합과 정확히 일치하고 대표 사진이 최대 한 장인지 확인하여 다른 초안 사진의 혼입이나 누락 갱신을 거부한다.

07 / CATEGORY & MAP EXPLORATION

맛집·여행지 카테고리와 지도 탐색

모든 공개 게시물은 맛집 또는 여행지 중 하나의 대표 카테고리를 갖는다. 사용자는 카테고리를 선택하고, 개별 게시물을 차례로 읽는 리스트와 전체 분포를 보는 지도 사이를 자유롭게 전환한다.

🍽️

맛집

식당·카페·바·디저트 가게 기록. 공통 게시물 정보에 평점, 추천 메뉴, 가격대, 대기시간, 재방문 의사를 선택적으로 추가한다.

🧭

여행지

명소·자연·문화시설·쇼핑·체험 기록. 추천 방문 시간, 소요 시간, 볼거리, 여행 팁, 계절 정보를 선택적으로 추가한다.

분류 규칙: 대표 카테고리는 정확히 하나만 선택한다. 카페·디저트·사찰·전망대처럼 더 자세한 분류는 복수 태그로 추가해 카테고리 구조가 복잡해지는 것을 막는다.

맛집 전용 입력 규칙

항목입력 방식저장 규칙
평점0.5점 단위, 최대 5.0점선택하지 않으면 저장하지 않는다.

C14 구현 기준: 인증된 소유자 요청이 업로드 항목별 작업을 한 번에 하나씩 잠그고 실행한다. JPG·PNG는 최대 2,500만 픽셀까지 방향을 적용한 뒤 품질 0.92 JPEG로 새로 인코딩하고 EXIF·XMP·IPTC 재검사를 통과한 결과만 비공개 SANITIZED_MASTER로 저장한다. 자산 저장과 메타데이터 검사가 모두 성공한 사진만 READY로 전환하며, 완료 요청을 다시 보내도 같은 사진의 완료 상태를 복구한다. V11 마이그레이션은 이 조건을 이미 충족했지만 과거 버전에서 PROCESSING에 남은 사진만 READY로 백필한다. 현재 운영 JVM에서 HEIC·HEIF 픽셀 디코더가 검증되지 않았으므로 해당 형식은 공개하지 않고 JPEG 변환 후 재업로드를 안내한다. 임시 원본 삭제는 공개 파생본까지 검사하는 C17에서 수행한다.
C15 구현 기준: 메타데이터 검사를 통과한 정제 마스터에서 긴 변 기준 THUMBNAIL 320px, MAP_CARD 960px, PUBLIC_DETAIL 2000px JPEG를 생성한다. 작은 사진은 확대하지 않고 비율을 유지하며, 각 결과를 다시 메타데이터 검사한 뒤 비공개 variants/ 경로와 사진 자산에 기록한다. 신규 사진은 세 파생본까지 저장돼야 READY가 되며, 기존 완료 사진은 정제 요청 재호출 시 누락된 유형만 보충한다. C16이 픽셀 워터마크를 합성하고 공개 전환하기 전까지 모든 파생본은 비공개다.
C16 구현 기준: 세 반응형 파생본의 하단 오른쪽에 Places & Plates를 이미지 너비의 16%, 가장자리 3% 여백, 28% 불투명도로 픽셀 합성한다. 합성 영역의 평균 밝기에 따라 흰색 또는 검은색을 선택하고, JPEG 재인코딩과 메타데이터 재검사를 통과한 자산만 논리적 PUBLIC으로 전환한다. 정제 마스터는 계속 비공개이며 파생본에는 places-plates-corner-v1 정책 버전과 BOTTOM_RIGHT 위치를 기록한다. 기존 C15 파생본이나 정책 버전이 다른 자산은 업로드 원본이 아니라 정제 마스터에서 다시 생성한다. 실제 공개 조회는 게시물의 PUBLISHED·PUBLIC 조건도 함께 만족해야 한다.
C17 구현 기준: 세 파생본은 저장 직후에는 비공개다. 서버가 저장소에서 정제 마스터와 파생본을 다시 내려받아 JPEG 디코딩, 기록된 바이트 크기·해상도, EXIF·XMP·IPTC 0건을 확인하고 정제 마스터에서 같은 워터마크 정책으로 재생성한 픽셀 바이트와 일치할 때만 논리적 PUBLIC으로 전환한다. 그 뒤 temporary/ 원본 삭제까지 성공해야 업로드 항목을 COMPLETED, 사진을 READY로 바꾼다. 삭제 실패는 원본 키와 비공개 처리 상태를 유지해 재시도하고, 검증 실패는 사진을 FAILED로 차단한 채 원본을 삭제한다. 처리되지 않은 원본은 24시간 만료와 예약 정리로 폐기하며 정리 조회도 소유자 RLS 경계 안에서 수행한다.
C23 구현 기준: 소유자는 초안 편집 화면에서 비공개·링크 공개·전체 공개 중 하나를 고른다. 서버는 게시 요청 시 제목·방문 월·한줄평·장소·사진·대표 사진을 다시 확인하고, 모든 사진의 READY, 임시 원본 삭제 완료, 비공개 정제 마스터의 메타데이터 검사, 세 공개 파생본의 places-plates-corner-v1·BOTTOM_RIGHT 워터마크 정책을 한 번 더 검사한다. 모든 조건을 통과한 소유자 초안만 선택한 범위의 PUBLISHED로 전환하며, 링크 공개의 추측 불가능한 공유 주소와 실제 공개 읽기 화면은 C24~C27 조회 API·상세 페이지에서 연결한다.
C24 구현 기준: 공개 기록 목록은 비로그인 GET /api/v1/public/posts에서 visibility=PUBLIC과 status=PUBLISHED를 명시적으로 함께 검사하고 PostgreSQL PUBLIC RLS를 한 번 더 적용한다. 응답은 소유자 ID·본문·내부 장소 ID를 제외하고 제목·한줄평·월 단위 방문 시기·카테고리·게시 시각과 전체·맛집·여행지 합계만 제공한다. /posts의 링크 기반 탭은 URL 쿼리로 선택 상태를 유지하며 로딩·카테고리별 빈 목록·API 장애를 구분한다. 대표 사진과 정렬은 C25에서 추가한다.
C25 구현 기준: 공개 목록은 sort=LATEST|OLDEST를 게시 시각과 ID의 같은 방향으로 정렬해 결과를 안정화하고, 카테고리 링크를 바꿔도 선택한 정렬을 URL에 유지한다. 카드는 대표 사진·카테고리·제목·한줄평·월 단위 방문 시기를 한 화면에 표시한다. 대표 사진은 READY 대표 사진의 MAP_CARD 중 PUBLIC·메타데이터 검사·픽셀 워터마크·현재 정책을 모두 통과한 자산만 비로그인 GET /api/v1/public/posts/{postId}/cover로 제공한다. 없는 공개 대표 사진은 인증 여부와 관계없이 JSON 404, 지원하지 않는 정렬·카테고리 값은 400 COMMON_INVALID_QUERY로 반환하며 오류 응답이 요청 트랜잭션 종료 시 다른 상태로 바뀌지 않게 한다. UI 보호 레이어는 일반적인 우클릭 저장을 억제하는 보조 수단이며 복사나 화면 캡처의 완전한 차단을 보장하지 않는다. 원본·정제 마스터·Storage 키는 공개하지 않는다.
C26 구현 기준: 공개 목록 카드에서 /posts/{postId}의 반응형 읽기 화면을 열고 사진·개인 기록·카테고리 전용 정보 순서로 읽는다. 비로그인 GET /api/v1/public/posts/{postId}는 PUBLIC + PUBLISHED만 반환하며 공통 기록과 현재 카테고리의 맛집 또는 여행지 정보만 포함한다. 공개 방문 시기는 연·월만, 장소는 이름과 Google 지도 링크만 제공하고 소유자 ID·내부 장소 ID·좌표·게시 일자·Storage 키는 제외한다. 상세 사진은 READY 사진의 PUBLIC_DETAIL 중 공개 접근·메타데이터 검사·픽셀 워터마크·현재 정책을 모두 통과한 자산만 별도 사진 API로 제공한다. 비공개 파생본과 원본·정제 마스터는 상세 응답과 사진 API 모두에서 찾을 수 없는 것으로 처리한다.
C27 구현 기준: 상세 화면의 장소 링크는 내부 장소 ID를 노출하지 않고 현재 공개 게시물 ID를 사용하는 /posts/{postId}/place로 이동한다. 비로그인 GET /api/v1/public/posts/{postId}/place는 진입 게시물이 PUBLIC + PUBLISHED일 때만 같은 소유자·장소의 전체 공개 기록을 공개 방문 연·월 기준 오래된 순으로 반환한다. 장소 화면은 방문 수, 장소명, Google 지도 링크, 검증된 MAP_CARD 대표 사진과 각 상세 링크를 표시한다. 다른 회원의 기록, 링크 공개·비공개 게시물, 내부 소유자·장소 ID, 좌표, 게시 시각은 제외하며 PostgreSQL V15는 공개 게시물에 연결된 장소 행만 PUBLIC RLS로 읽게 한다.
C29 구현 기준: 비로그인 GET /api/v1/map/posts는 PUBLIC + PUBLISHED, 장소 좌표, 게시물의 좌표 공개 허용을 모두 만족하는 기록만 반환한다. Google 장소 좌표는 refreshed_at이 30일을 넘으면 제외하고 다시 장소를 선택해 갱신하도록 하며, APPROXIMATE 좌표는 소수점 둘째 자리로 낮춰 응답한다. /map은 전체·맛집·여행지 URL 필터를 API와 일치시키고 맛집은 주황색 ‘맛’, 여행지는 초록색 ‘여’ 마커로 표시한다. Google Maps JavaScript API는 사용자가 “지도 불러오기”를 누를 때만 로드하며 브라우저 키는 HTTP 리퍼러와 Maps JavaScript API로 제한한다. Map ID가 있으면 Advanced Marker를, 없으면 기본 마커 호환 경로를 사용한다. 같은 위치 묶음·영역 합계·지도 중심 레이아웃은 C30~C32에서 이어간다.
C30 구현 기준: 공개 지도 결과는 @googlemaps/markerclusterer의 Supercluster로 화면 픽셀 거리가 가까운 마커를 확대 수준별로 묶는다. 묶음 원 안의 숫자는 필터된 공개 게시물 포함 수를 그대로 사용하고, 선택하면 기본 클러스터 범위로 확대해 개별 마커로 분리한다. 맛집만 또는 여행지만 포함한 묶음은 해당 카테고리 색상, 두 카테고리가 섞인 묶음은 브랜드 색상으로 표시한다. Map ID가 있는 Advanced Marker와 없는 기본 Marker 경로 모두 같은 숫자·클릭 동작을 제공하고, 현재 화면 합계는 C31에서 별도로 계산한다.
C31 구현 기준: 현재 지도 영역 합계는 클러스터 개수가 아니라 이미 공개 범위와 URL 카테고리 필터를 통과한 개별 게시물 좌표를 현재 LatLngBounds와 비교해 계산한다. 지도의 최초 맞춤, 이동, 확대·축소가 끝나는 idle 이벤트마다 별도 지연 없이 전체·맛집·여행지 수를 갱신해 500ms 이내 기준을 지킨다. 날짜 변경선을 가로지르는 경계도 처리하며 지도 로드 전에는 영역 합계를 표시하거나 Maps JavaScript API를 요청하지 않는다.
C32 구현 기준: 지도 탭은 PC에서 지도 70%·축소 게시물 목록 30%, 980px 이하에서 큰 지도 다음 가로 스크롤 카드로 구성한다. 제목·장소명 검색은 기존 지도 인스턴스를 다시 만들지 않고 클러스터에 포함되는 마커와 축소 목록만 갱신하며, “현재 지도 영역만 보기”로 화면 경계의 카드를 좁힌다. 카드 선택은 해당 마커로 이동해 정보창을 열고, 마커 선택은 대응 카드를 선택·스크롤하며, 카드 hover·focus는 마커를 강조한다. 검색어·선택 게시물·지도 중심·확대 수준·지도 로드 여부는 URL에 보존해 카테고리 전환 후 복원하고, /posts의 기존 큰 카드 구성은 변경하지 않는다.
C33 검증 기준: 지도 숫자는 장소 수가 아닌 필터된 공개 게시물 수를 기준으로 한다. 자동 테스트는 전체·맛집·여행지 API 합계, 일반 경계와 날짜 변경선 영역 합계, 실제 포함 마커 기반 단일·혼합 카테고리 묶음 숫자, 같은 소유자·장소의 공개 재방문 수와 월순 정렬을 함께 확인한다. 같은 좌표의 재방문 게시물도 각각 한 건으로 세며 비공개·링크 공개·다른 소유자 기록은 장소 이력에서 제외한다.
C34 구현 기준: 공개 목록 카드·상세 갤러리·장소 이력 사진은 하나의 보호 컴포넌트를 사용해 우클릭 메뉴, 이미지 드래그·복사와 모바일 길게 누르기의 기본 동작을 억제한다. Cloud Run 대표·상세 사진 API와 Vercel의 같은 출처 /api/public-images/** 중계 응답은 Cross-Origin-Resource-Policy: same-origin, frame-ancestors 'none', X-Frame-Options: DENY를 적용해 외부 브라우저의 직접 이미지 삽입과 프레임 표시를 줄인다. Vercel /_next/image 최적화 계층이 사용자 정의 보안 헤더를 보존하지 않는 운영 결과를 반영해, 이미 정제·리사이즈·워터마크된 파생본은 unoptimized로 같은 출처 중계 경로에서 직접 제공한다. 서버 프록시·개발자 도구·화면 캡처는 막을 수 없으므로 이 기능은 원본 미제공·메타데이터 제거·픽셀 워터마크와 구분되는 보조 억제 기능이다.
C28 검증 기준: 전체·맛집·여행지 목록과 합계, 게시물 상세, MAP_CARD 대표 사진, PUBLIC_DETAIL 상세 사진, 같은 장소 이력을 하나의 공개 범위 회귀 묶음으로 확인한다. 애플리케이션 API와 실제 PostgreSQL RLS 모두 PUBLIC + PUBLISHED 조합만 허용하며 PUBLIC + DRAFT, UNLISTED + PUBLISHED, PRIVATE + PUBLISHED와 그 게시물에 연결된 카테고리 상세·장소·사진·자산은 목록에서 제외하고 직접 URL에도 404를 반환한다.

사진 처리와 위치 정보는 비용과 개인정보에 직접 영향을 주므로 임시 업로드 원본, 정제 마스터, 공개 이미지를 분리하고 모든 기록에 소유자 경계를 둔다.

frontend

독립된 Next.js + TypeScript 프로젝트. 페이지는 app, 기능은 domain, 공통 요소는 shared로 나눠 Spring Boot와 비슷하게 책임을 드러낸다.

backend

독립된 Java + Spring Boot + Gradle REST API. 도메인별 controller·service·repository·entity·dto 구조와 Spring Security 소유자 권한을 적용하며, Cloud Run은 Java 21과 이미지 색상 처리용 LCMS2가 포함된 비루트 컨테이너로 실행한다.

이미지 파이프라인

인증된 처리 요청이 임시 원본을 방향 보정·재인코딩해 비공개 정제 마스터를 만들고, 이후 공개 파생본 검사까지 끝나면 임시 원본을 삭제한다.

Google 지도 연결

Google Maps JavaScript API와 Places API (New)를 사용한다. 장소 검색은 Spring Boot에서 명시적 요청마다 최대 5건만 수행하고 결과에 Google Maps 출처를 표시한다. Place ID는 장기 보관하고 좌표 스냅샷은 30일 안에 갱신하며, 검색 실패 시 직접 입력을 제공한다.

탐색 인덱스

게시 상태·카테고리·좌표를 함께 조회하고 지도 경계 및 묶음 단위 집계를 빠르게 계산한다.

저장소 구조: 하나의 Git 저장소 아래 frontend/와 backend/를 두는 모노레포로 운영한다. 프론트엔드의 인증·게시물·저장소 제어는 /api/v1 Spring Boot API만 호출한다. 사진 본문은 백엔드가 소유자와 UUID 객체 키를 검증해 발급한 단기 서명 토큰으로 Supabase Storage TUS 엔드포인트에 직접 전송하며 서비스 역할 키는 브라우저에 노출하지 않는다. 운영 PostgreSQL은 Supabase를 사용하며 관리자 마이그레이션 역할과 RLS가 강제되는 애플리케이션 역할을 분리한다. 로그인 세션도 PostgreSQL에 저장해 Cloud Run 리비전 교체나 다중 인스턴스 전환 후 인증을 복구한다. 상세 규칙은 PROJECT_STRUCTURE.md와 docs/SUPABASE_DATABASE.md를 기준으로 한다.
실패 시 안전하게 닫기: 메타데이터 제거, 워터마크 생성 또는 게시 전 검사 중 하나라도 실패하면 임시 원본을 공개하지 않는다. 사진은 비공개 처리 상태에 머물고, 재시도 만료 후 임시 원본을 자동 삭제하며 필요하면 사용자가 다시 업로드한다.
13 / PHASES

제작 순서

화려한 홈 화면보다 업로드→초안→상세 기록의 핵심 루프를 먼저 완성한 뒤 탐색 기능을 확장한다.

Phase 1

안전한 기록·탐색 루프

인증, 사진 보호 파이프라인, 초안, 맛집·여행지, 리스트, 지도·묶음 수, 장소 연결, 상세 페이지

Phase 2

고급 탐색 경험

여행 타임라인, 연도·태그·평점 필터, 사진 모아보기, 일괄 편집, 지도 성능 최적화

Phase 3

회원·커뮤니티 확장

일반 회원가입, 사용자별 고유 페이지, 공개 프로필 탐색과 링크 공유. 각 회원은 본인 기록만 편집하며 타인의 페이지는 열람한다.

결정 항목현재 권장안영향
